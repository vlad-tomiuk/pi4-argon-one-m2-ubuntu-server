# Безпека

Головний принцип: **на роутері не відкривається жоден порт**. Назовні сервер виходить сам —
через Cloudflare Tunnel для публічних сайтів і через Tailscale для приватних сервісів.

```
                        ┌──────────────── СЕРВЕР ────────────────┐
                        │  Публічні сайти      Приватні сервіси  │
                        │  портфоліо           менеджер паролів  │
                        │  інші проєкти        закладки, диск    │
                        └────────▲──────────────────▲────────────┘
                                 │                  │
                      Cloudflare Tunnel        Tailscale
                                 │                  │
                          інтернет, будь-хто   лише твої пристрої
```

## Що вмикає встановлення

| Механізм | Деталі |
|---|---|
| **UFW** | вхідні закриті; дозволені лише SSH і mDNS з локальної мережі |
| **SSH** | root заборонений, ключі обов'язкові, пароль приймається **тільки з локальної мережі**, 3 спроби, таймаут 30 с |
| **fail2ban** | бан після 5 невдалих спроб, час бану зростає до тижня |
| **Автооновлення** | безпекові оновлення ставляться самі |
| **sysctl** | SYN cookies, заборона redirects і source routing, обмеження `dmesg` і вказівників ядра |
| **Watchdog** | апаратний таймер перезавантажує Pi при зависанні; kernel panic → reboot через 10 с |
| **fsck** | автоматичний ремонт файлової системи після зникнення живлення |

Перевірити все одразу: `sudo server-status` — розділ «Захист».

## Обов'язковий крок після встановлення: SSH-ключ

Пароль поки що працює з локальної мережі, але ключ надійніший:

```bash
ssh-keygen -t ed25519
ssh-copy-id ТВІЙ_ЮЗЕР@server.local
```

З Windows:

```powershell
ssh-keygen -t ed25519
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh vlad@server "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"
```

## Docker обходить UFW

Це не помилка налаштування, а те, як працює Docker: опубліковані порти додаються в iptables
раніше за правила UFW. Тому:

```yaml
ports:
  - "127.0.0.1:8080:80"   # правильно: доступно лише самому серверу
  - "8080:80"             # доступно всій локальній мережі попри UFW
```

Сервіси, які мають бути видимі назовні, публікуй на `127.0.0.1` і віддавай через
Cloudflare Tunnel або Tailscale — обидва підключаються до контейнера зсередини сервера.

## Tailscale для приватного доступу

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
sudo ufw allow in on tailscale0 comment 'Tailscale'
```

В адмінці: **Disable key expiry** для сервера, **MagicDNS** і **HTTPS Certificates**.

Опублікувати локальний сервіс у своїй мережі з HTTPS:

```bash
sudo tailscale serve --bg 8080                    # → https://server.tailXXXX.ts.net
sudo tailscale serve --service=svc:vault --bg 8080  # → https://vault.tailXXXX.ts.net
tailscale serve status
```

Другий варіант — **Tailscale Services**: кожен сервіс отримує власне ім'я без портів.
Вузол при цьому має бути тегованим (`tailscale up --advertise-tags=tag:server`), а хост
сервісу — підтвердженим в адмінці.

**Tailscale Funnel не вмикай**, якщо не розумієш наслідків: він виставляє сервіс у публічний
інтернет. Для сховища паролів це неприйнятно.

```bash
sudo tailscale funnel off           # якщо випадково увімкнувся
```

## Cloudflare Tunnel для публічних сайтів

`cloudflared` запускається контейнером поруч із сайтом і сам підключається до Cloudflare.
Вхідні порти не потрібні, справжній IP сервера не світиться. Сайти при цьому не мають
публікувати порти в мережу — тільки `127.0.0.1` або спільна docker-мережа з `cloudflared`.

## Швидкий аудит

```bash
sudo server-status                  # загальна картина
ss -tulnp | grep -v 127.0.0.1       # що слухає назовні
sudo ufw status numbered            # правила файрвола
sudo fail2ban-client status sshd    # бани
who; last -n 20                     # хто заходив
journalctl -u ssh --since "-24h" | grep -i fail
docker ps --format '{{.Names}}\t{{.Ports}}'
```

Найважливіший рядок у `server-status` — **«Слухають порти»**. Усе, чого ти там не впізнаєш,
варто з'ясувати.

## Паролі, яких буде кілька

| Пароль | Де використовується | Де зберігати |
|---|---|---|
| системний | SSH і `sudo` | у менеджері паролів |
| Samba | мережевий диск | у менеджері паролів |
| панель адміністратора Vaultwarden | сторінка `/admin` | у менеджері паролів |
| **головний пароль сховища** | саме сховище | **тільки в голові й на папері** |

Не використовуй системний пароль для інших сервісів: компрометація одного з них не повинна
відкривати доступ до SSH.

## Чого тут навмисно немає

- **Шифрування диска** — на Pi воно вимагає введення пароля при кожному завантаженні, що
  несумісне з автовідновленням після зникнення світла. Vaultwarden і так шифрує дані на
  клієнті, тому в базі вони вже зашифровані.
- **Проброс портів на роутері** — замінений тунелями.
- **Вхід по паролю з інтернету** — вимкнений назавжди.
